# HELIOS Phase 15 — security and privacy hardening report

Assessment date: 2026-09-13. Scope: the repository in this workspace, not a deployed system. **This prototype is not approved for real patient data.** No claim of 100% security or regulatory compliance is made. See `docs/security.md` for the operating model and detailed limitations.

1. **Security architecture — PARTIAL.** Separate patient and doctor UIs call the same Express API and PostgreSQL/Prisma model. Server-side signed session proofs, ownership checks, clinician assignments, private file access and clinical audit writes provide boundaries. Clinic/department tenancy, database row-level security, deployment controls, and independent penetration testing remain absent.
2. **Authentication changes — PARTIAL.** HMAC-SHA256 tokens have role-specific kind and configurable expiration; signatures are compared safely and malformed tokens are rejected. Patient tokens moved from localStorage to sessionStorage. Clinician access still uses a demo code, with no production IdP/MFA, account recovery, token revocation, logout invalidation, refresh rotation, or signing-key rotation.
3. **Authorization/RBAC changes — PARTIAL.** Patient service reads/writes require a proof and stored session ownership. Doctor dashboard, comparison, brief, verification, AYUSH and queue services check an active clinician and patient assignment; admin bypass is explicit where supported. There is no production admin management or clinic hierarchy.
4. **Patient isolation verification — PARTIAL.** Profile, visit, consent, complaint, submission, documents, voice, timeline and AYUSH flows use server-side session/patient checks. Patient profile and visit responses were minimized. Live A/B database tests are still required; eight PostgreSQL-gated integration tests were skipped.
5. **API security changes — PARTIAL.** Strict Zod schemas on key mutation inputs, bounded JSON bodies, endpoint-group rate limits, Origin check, no-store, CORS allowlist, secure headers, generic not-found errors and request IDs. Rate limit is per-process/IP and can be too broad behind NAT; it is not a distributed abuse control. Full route-by-route parameter pollution, prototype pollution, and fuzz coverage remains.
6. **Document/voice security — PARTIAL.** Uploads have limits, file-type/signature checks, generated private keys, no public mount, authorization and restrictive previews; local document deletion also removes stored bytes. Active-PDF rejection is heuristic. No malware scanner, isolated converter, complete polyglot defense, encryption-at-rest verification, or complete file lifecycle policy. Raw audio is not intentionally retained.
7. **AI security — PARTIAL.** Model/OCR outputs are untrusted, schema-validated data and cannot directly execute privileged actions. The optional clinical NLU provider receives minimal answer/question/relevant-fact context with remote storage disabled; speech receives audio to transcribe. Prompt injection may still influence clinical _content_ and requires clinician review. The Phase 5 SafetyEngine referenced in the request is **NOT IMPLEMENTED** in this repository.
8. **Secret management — PARTIAL.** Server keys are environment-only; production rejects default session secret, enabled demo mode, default doctor demo code, and a public storage path. A source scan found only placeholder local/test DB URLs. Historical commits, built artifacts, CI stores and deployed secrets were not independently scanned or rotated.
9. **Database security — PARTIAL.** Prisma queries, migrations, indexes and transactions are used in core workflows. Least-privilege DB accounts, TLS/network isolation, RLS, encrypted backups and restore testing are infrastructure work not verified here. Verification queue facts and metrics were narrowed to assigned patients.
10. **Logging/audit changes — PARTIAL.** Request logging omits bodies/headers/query strings and masks resource-shaped paths. Security events use hashed actor references. Clinical verification and queue mutations retain audit records. Audit coverage, immutable storage, read-access audit, retention, and production sink permissions remain incomplete.
11. **Privacy/retention changes — PARTIAL.** Intake consent exists and raw audio is not deliberately stored. Document deletion removes originals/processed bytes. Consent withdrawal, data-subject deletion, session/transcript/log/audit retention schedules, backup deletion, and legal review are outstanding.
12. **Dependency audit — IMPLEMENTED for this snapshot.** `pnpm audit --prod --audit-level high` initially found 3 high-severity transitive issues: two PostCSS and one deepmerge-ts. Pnpm overrides and lockfile refresh now resolve patched versions; repeat audit reported no known vulnerabilities. This result expires as advisories change. Advisory references: [PostCSS arbitrary file read](https://github.com/advisories/GHSA-6g55-p6wh-862q), [PostCSS path traversal](https://github.com/advisories/GHSA-r28c-9q8g-f849), [deepmerge-ts stack exhaustion](https://github.com/advisories/GHSA-ggr8-5vv4-36mx).
13. **Security tests — PARTIAL.** `pnpm test` passes 233 API and 33 web tests. Five dedicated hardening tests cover token expiry/role separation/signature tampering, cross-origin mutation, creation throttling, response secret absence, and patient BOLA/duplicate-visit denial. Existing upload, clinician, verification and queue suites cover further negative paths. Eight DB-dependent tests are skipped.
14. **Attack simulations — PARTIAL.** Automated negative paths include invalid/expired/wrong-kind tokens, malformed signature, cross-origin mutation and repeated session creation; existing tests cover upload rejection and selected unauthorized clinical actions. The full 17-scenario acceptance matrix in the user specification is not yet proven in a live deployment or real multi-patient PostgreSQL database.
15. **Remaining vulnerabilities.** Demo clinician credential; token revocation absent; frontend tokens remain readable to injected script; rate limits process-local; document scanning heuristic; weak inline-script CSP; no automatic clinical data retention; no database tenant isolation; incomplete audit integrity; no production backup/restore verification; no SafetyEngine.
16. **Known limitations.** No configured live PostgreSQL instance or deployed HTTPS/proxy environment for this assessment. API unit tests with mocked services do not prove storage-level BOLA behavior. Current public bootstrap creates patient sessions without an identity check, merely throttled per IP. Production deployment should be blocked until identity, infrastructure and privacy controls are designed and validated.
17. **Files changed.** Principal areas: `apps/api/src/security/*`, `apps/api/src/middleware/*`, `apps/api/src/services/patient-flow-service.ts`, `apps/api/src/repositories/*`, `apps/api/src/{comparison,clinical-brief,verification,ayush,document-ai}/*`, `apps/api/src/routes/*`, `apps/web/src/providers/patient-flow-provider.tsx`, `apps/web/src/services/patient-flow.ts`, `apps/web/next.config.ts`, `apps/api/tests/security/hardening.test.ts`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `.env.example`, and `docs/security.md`. This lists Phase 15 areas, not every pre-existing file.
18. **Commands used.** `pnpm install`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm audit --prod --audit-level high`, targeted Vitest runs and scoped source/secret scans. The final audit returned no known vulnerabilities; all listed local checks passed except the eight explicitly skipped DB tests.
19. **Production security checklist — NOT COMPLETE.** Before real data: replace demo clinician login with production identity/MFA; implement logout/revocation and key rotation; deploy distributed abuse controls; finish and run live A/B patient/doctor/admin tests; validate backup encryption and restore; implement retention/withdrawal/deletion; add malware/sandbox processing; remove inline-script CSP dependence; test TLS/proxy/CORS in deployment; make audit storage tamper-resistant; perform vendor, legal/privacy and independent security reviews; either implement/test SafetyEngine or remove product claims about it.

Status terms describe evidence in this repository on the assessment date only. “IMPLEMENTED” for dependency audit means the audit/remediation workflow was executed, not that all dependencies are permanently safe.
