HELIOS PROJECT GUIDE FROM GROUND ZERO
=====================================

Snapshot covered: implementation through Phase 12
Project name: HELIOS - Healthcare Enabled Language & Intelligent Observation System
Proposal context: Smart India Hackathon 2026, SIH26047
Repository type: pnpm TypeScript monorepo
Primary purpose: consent-first pre-consultation case taking that helps a patient describe their health story and helps a doctor review structured, source-aware information.

IMPORTANT SAFETY STATEMENT
--------------------------

HELIOS is an information-capture, organization, comparison, and human-review system. It is not a diagnosis system, prescription system, treatment recommender, autonomous triage tool, medical device, or proof of regulatory compliance. Phase 5 SafetyEngine is NOT implemented. RiskSignal exists as a storage/read model only. Existing stored risk information may be displayed, but this code does not calculate clinical risk.

This guide describes the actual checked-out code. It does not treat plans in old documents as implemented features.


1. THE ONE-PARAGRAPH MENTAL MODEL
---------------------------------

A patient opens the Next.js web app, starts or resumes a signed session, selects English or Hindi, explicitly consents, enters basic details and a chief complaint, and completes a deterministic adaptive interview by text, choices, or confirmed speech. Optional medical documents can be uploaded to private storage, processed with bounded OCR/extraction, and reviewed fact by fact. Confirmed information is stored in PostgreSQL through Prisma with explicit provenance and knowledge states. A rebuildable timeline projects source records without replacing them. Doctors can compare two visits, read a short evidence-linked Clinical Brief, verify/correct/reject facts through an immutable action ledger, and review AYUSH use. A multilingual layer separates original source content, language-neutral facts, and replaceable display translations. Every important boundary favors unknown, conflict, clarification, evidence, and human confirmation over unsupported certainty.

5. APPLICATION BOOT SEQUENCE
----------------------------

API:
  1. apps/api/src/config/env.ts reads and validates environment variables.
  2. PrismaDatabaseService creates the shared Prisma client wrapper.
  3. Provider factories choose mock/local/OpenAI behavior from server config.
  4. createApp() composes patient, voice, interview, document, timeline, comparison, brief, verification, AYUSH, and language services.
  5. Express disables x-powered-by.
  6. Middleware installs request IDs, structured logging, Helmet, CORS, and 1 MB JSON/form limits.
  7. Health routes and all /api/v1 routers are mounted.
  8. Not-found and centralized error middleware are installed last.
  9. server.ts listens on PORT, sets request/header/keep-alive timeouts, and disconnects Prisma on SIGINT/SIGTERM.

Web:
  1. Next.js serves the root role-selection page and patient/doctor routes.
  2. PatientLayout wraps patient pages in PatientFlowProvider.
  3. PatientFlowProvider hydrates identifiers/navigation from localStorage and temporary form drafts from sessionStorage.
  4. Typed service modules call NEXT_PUBLIC_API_URL.
  5. Server session DTOs rehydrate authoritative patient/visit/progress data.
  6. The shared language registry and useTranslation select supported display strings.

  Shows the visit token, explains what happens next, links to the patient timeline, and can clear the local session.

/doctor/verification
  Verification Center queue, detail, side-by-side source/current facts, conflict handling, and explicit verification actions.

/doctor/patients/[patientId]/ayush

8. API ARCHITECTURE RULE
------------------------

The normal dependency direction is:

  route -> validation/upload middleware -> controller -> service/engine -> repository -> Prisma -> PostgreSQL

Routes define URLs and middleware order.
Validation modules treat every body/parameter/query as untrusted.
Controllers translate HTTP requests and write standard response envelopes.
Services enforce workflow, authorization/ownership, transactions, and cross-domain orchestration.
Engines perform deterministic domain calculations.
Repositories contain Prisma reads/writes and transaction details.
Serializers prevent raw Prisma/private provider/storage details from leaking to clients.
Shared DTOs keep web/API contracts consistent.

Successful envelope:
  { "success": true, "data": ... }

Error envelope:
  { "success": false, "error": { "code": "...", "message": "...", "requestId": "..." } }

10. PATIENT FLOW IN DETAIL
--------------------------

New session:
  - POST /patient-sessions creates PatientSession with English default.
  - SessionProofService signs an opaque token using SESSION_TOKEN_SECRET.
  - The client stores token and session ID for subsequent ownership-bound work.

Language:
  - Initial LANGUAGE progress advances to CONSENT.
  - A later language switch keeps currentStep unchanged.
  - When a patient already exists, SessionRepository synchronizes preferredLanguage.

Consent:
  - Checkbox must be explicit; API schema only accepts accepted=true.
  - ConsentRecord stores type, version, time, session, and optional patient link.
  - Session advances to BASIC_INFO.

Details:
  - Name uses Unicode-aware validation.
  - Age must be an integer from 0 through 120.
  - Sex is a controlled enum.
  - Phone is optional and format-bounded.
  - IntakeRepository creates patient and visit and binds the session transactionally.

Complaint:
  - Original patient wording is stored as chiefComplaint.
  - Simple health-detail fields may also be persisted.
  - Changing complaint in browser state clears an existing interview ID so the pathway is not silently reused.

Interview:
  - Server classifies one of six complaint pathways.
  - One localized question is rendered at a time.
  - A response is interpreted and previewed before confirmation.
  - Confirming atomically updates persisted interview state.
  - Unknown and conflicts remain explicit.
  - Required fields and dependency conditions determine completeness.
  - The patient can revise an answer before completion.
  - Completion materializes ClinicalHistory; it does not diagnose.

Documents:
  - Entirely optional.
  - Patient can skip directly to review.
  - Uploaded material is not accepted as truth without visible extraction status and fact review.

Review/submission:
  - Patient can return to edit earlier sections.
  - Submit changes PatientSession to COMPLETED and Visit to READY_FOR_DOCTOR.
  - Visit projection is added/updated in the timeline.
  - Complete screen shows a visit token and next-step explanation.


11. ADAPTIVE INTERVIEW ENGINE
-----------------------------

Implemented complaint pathways:
  abdominal_pain
  chest_discomfort
  headache
  fever
  cough_breathing
  general_pain (fallback)

Common required HPI fields per standard pathway:
  location
  duration
  severity 0-10
  associatedSymptoms

Abdominal pain adds:
  vomitingFrequency when vomiting is selected
  optional pain character

Common conditional AYUSH branch:
  ayushUse
  ayushSystem
  ayushTreatment
  ayushRecommendedBy
  ayushStarted
  ayushUseStatus
  ayushNewSymptoms
  ayushReportedEffect when new symptoms are reported

Supported input types:
  TEXT, LONG_TEXT, VOICE, CHOICE, MULTI_SELECT, YES_NO,
  NUMBER, DATE, DURATION, SLIDER.

Question selection:
  - Clarifications have priority 1000.
  - Otherwise the highest-priority active required uncaptured question wins.
  - Dependency-controlled questions activate only when their parent value matches.
  - The browser never decides sequencing.

Knowledge states:
  YES              Positive/captured information.
  NO               Explicit negative response.
  UNKNOWN          Patient does not know or interpretation is unsafe.
  NOT_ASKED        Not yet captured/reopened for revision.
  NOT_APPLICABLE   Explicitly not applicable.
  CONFLICT         Two captured values disagree; clarification required.

NLU behavior:
  - ClinicalNLUService sees the current question, answer, and at most one relevant existing fact.
  - Deterministic rules are the default.
  - Optional OpenAI output must satisfy a strict schema.
  - One constrained retry is allowed, then deterministic fallback.
  - Provider metadata may be stored in AIInteraction.
  - Model output cannot control question order or verify a fact.


12. VOICE SYSTEM
----------------

Browser states:
  IDLE
  PERMISSION_REQUEST
  READY
  RECORDING
  STOPPING
  UPLOADING
  TRANSCRIBING
  TRANSCRIBED
  AWAITING_CONFIRMATION
  EDITING
  CONFIRMED
  ERROR
  CANCELLED

Browser responsibilities:
  - Ask for microphone permission.
  - Choose a supported MediaRecorder MIME type.
  - Show local Web Audio amplitude; no network is needed for the waveform.
  - Stop at configured duration or patient action.
  - Upload Blob with declared language and opaque session proof.
  - Present text fallback when unavailable/denied/failed.

Server responsibilities:
  - Limit fields and bytes.
  - Validate MIME, extension, and signature-level bytes.
  - Ignore unsafe client filenames and create a provider-safe name.
  - Resolve session and visit server-side.
  - Apply provider timeout and normalized errors.
  - Persist original, optional normalized, patient-edited, and accepted transcript separately.
  - Mark retained=false and avoid storing raw audio.
  - Create a new VoiceInteraction for each retry instead of overwriting history.

Providers:
  mock     Safe deterministic default; no external key.
  openai   Optional server-side adapter selected by SPEECH_PROVIDER.

Only a patient-confirmed transcript is used downstream.


13. DOCUMENT INTELLIGENCE
-------------------------

Accepted high-level flow:
  preview -> upload -> validate -> hash -> private store -> process -> OCR pages
  -> classify -> extract -> normalize -> identity check -> patient review
  -> optional AYUSH projection -> timeline projection.

Security checks:
  - Signed session and patient/session ownership.
  - Bounded upload rate.
  - DOCUMENT_MAX_FILE_BYTES.
  - Allowed extension/MIME/magic signature.
  - Opaque private storage key and path traversal prevention.
  - Storage directory is never mounted publicly.
  - Patient-scoped SHA-256 duplicate detection.
  - Sanitized display filenames.
  - DOCUMENT_PROCESSING_TIMEOUT_MS.

Document types:
  PRESCRIPTION
  LAB_REPORT
  DISCHARGE_SUMMARY
  CONSULTATION_NOTE
  UNKNOWN

Processing statuses:
  UPLOADED, VALIDATING, PREPROCESSING, OCR_PROCESSING,
  LAYOUT_PROCESSING, EXTRACTING, NORMALIZING,
  REVIEW_REQUIRED, VERIFIED, FAILED, CANCELLED.

Evidence model:
  - DocumentPage stores ordered OCR text/confidence/dimensions.
  - DocumentFact stores original and normalized values, confidence, status, provenance, and language.
  - DocumentEvidence points a fact to page, exact source text, and optional bounding box.
  - Private storage paths are not included in public DTOs.

Patient actions:
  CONFIRM  Accept the extracted normalized fact for this workflow.
  EDIT     Change the normalized value while preserving source evidence.
  REJECT   Mark the extracted fact unusable; do not silently delete provenance.

Identity states:
  PENDING, MATCHED, IDENTITY_MISMATCH, NOT_PRESENT, MANUAL_OVERRIDE.
  A mismatch requires an explicit manual path before attaching its details.

Provider behavior:
  - Mock/text provider supports deterministic tests.
  - Local provider uses PDF.js, Sharp, and Tesseract.
  - Hindi medication frequency such as "din mein do baar" in Devanagari is mapped conservatively to twice daily while source text remains intact.


14. LONGITUDINAL TIMELINE
-------------------------

The timeline is a rebuildable index, NOT the source of truth.

Source inputs:
  visits, symptoms, clinical history, medications, allergies,
  observations, medical documents/document facts, doctor verifications,
  AYUSH records, and already-stored risk signals.

Pipeline:
  TimelineEventBuilder
    Performs source-specific conservative mapping.

  TimelineNormalizer
    Creates normalized keys and deterministic SHA-256 fingerprints.

  TimelineRepository
    Inserts/updates projections, stores versions, filters, pages, and details.

  TimelineConflictService
    Marks different values under the same semantic key without merging sources.

  TimelineAggregator
    Groups related visit/report events visually without collapsing facts.

  TimelineRebuildService
    Rebuilds one requested patient's timeline from source records.

  TimelineAuditService
    Records metadata-minimized view/rebuild activity.

Temporal rules:
  - eventDate is distinct from recordedAt and createdAt.
  - Precision is EXACT_DATE, MONTH_ONLY, YEAR_ONLY, DATE_RANGE, or UNKNOWN.
  - State is CURRENT, HISTORICAL, UNKNOWN, DISCONTINUED, or NOT_APPLICABLE.
  - Unknown dates sort after known dates.
  - Medication action is STARTED, REPORTED, CHANGED, CONFIRMED, or DISCONTINUED.
  - Historical does not imply discontinued; absence does not imply resolved.

Versioning:
  - Same fingerprint means no duplicate rewrite.
  - Changed projection first snapshots prior data into TimelineEventVersion.
  - Removed/rejected source creates a version and rejects the projection; history is not silently erased.


15. WHAT CHANGED COMPARISON
---------------------------

Purpose:
  Deterministically report recorded differences between two visit snapshots for a doctor. It does not interpret clinical importance, improvement, deterioration, or risk.

Pipeline:
  source records -> immutable PatientSnapshot for each visit
  -> normalization -> conservative entity matching -> field comparison
  -> classification -> evidence-linked ChangeRecord -> Comparison.

Change types:
  NEW
  REMOVED            Means absent from current recording, not clinically resolved.
  CHANGED
  UNCHANGED
  CONFLICTED
  UNKNOWN
  NOT_COMPARABLE
  NEWLY_CAPTURED

Entity types:
  SYMPTOM, MEDICATION, ALLERGY, OBSERVATION,
  CLINICAL_HISTORY_FIELD, DOCUMENT, RISK_SIGNAL, AYUSH_RECORD.

Match confidence:
  HIGH, MEDIUM, LOW, NONE.

Caching/staleness:
  - Snapshots are immutable and content-hashed.
  - Engine version and baseline/current hashes identify reusable output.
  - Source revisions mark an old comparison STALE.
  - Regeneration creates or reuses the correct current result.


16. CLINICAL BRIEF
------------------

Purpose:
  A concise doctor-facing view built from existing structured records. It does not run OCR, rebuild timelines, create comparisons, evaluate safety, diagnose, or recommend treatment.

Input bundle:
  current visit/patient snapshot,
  symptoms/history,
  medications/allergies,
  recent observations,
  recent documents,
  latest non-stale comparison,
  already-stored risk signals,
  AYUSH records.

Deterministic processing:
  - Apply BRIEF_RECENT_MONTHS and BRIEF_MAX_* limits.
  - Deduplicate and rank for compact display.
  - Create BriefClaim records with source IDs, provenance, confidence, and evidence.
  - Render template narrative from structured sections.

Sections:
  PATIENT_SNAPSHOT
  TODAYS_REASON
  CURRENT_SYMPTOMS
  WHAT_CHANGED
  RELEVANT_HISTORY
  MEDICATIONS
  ALLERGIES
  INVESTIGATIONS
  SAFETY_ATTENTION
  NEEDS_VERIFICATION
  SUPPORTING_DOCUMENTS
  SOURCE_EVIDENCE
  AYUSH_USE

Failure semantics:
  A failed/unavailable dependency is shown as UNAVAILABLE. It is never presented as "nothing found" or a reassuring negative.

Lifecycle:
  GENERATED -> REVIEWED or ARCHIVED.
  Source/verification/AYUSH changes may mark it STALE.
  Refresh builds or reuses a current version.


17. DOCTOR VERIFICATION
-----------------------

Core rule:
  Source provenance and verification state are independent. A patient-reported fact remains PATIENT_REPORTED after a doctor verifies it; the separate verification state becomes DOCTOR_VERIFIED.

Reviewable fact types:
  CLINICAL_HISTORY
  SYMPTOM
  MEDICATION
  ALLERGY
  OBSERVATION
  DOCUMENT_FACT
  INTERVIEW_RESPONSE
  AYUSH_RECORD

Actions:
  VERIFY
  CORRECT
  REJECT
  MARK_UNCERTAIN
  CONFIRM_CURRENT
  KEEP_PREVIOUS
  SUPERSEDE (internal lifecycle support)

Transaction:
  1. Verify doctor token and active role.
  2. Decode/validate opaque review ID.
  3. Resolve patient ownership, source, evidence, and current source version.
  4. Validate action-specific body and fact-type correction allowlist.
  5. Reject stale expected versions to prevent lost updates.
  6. Reuse a prior result for the same idempotency key.
  7. Append DoctorVerification with original and verified JSON values.
  8. Append metadata-minimized AuditLog.
  9. Update permitted source status/value/version.
 10. Commit atomically.
 11. Mark comparisons and briefs stale.
 12. Request timeline rebuild.

If step 12 fails after commit, the doctor decision remains saved and downstream views report that refresh is needed. An LLM has no route to perform a verification action.


18. AYUSH SUPPORT
-----------------

Purpose:

Systems:

19. MULTILINGUAL LAYER
----------------------

Three separate representations:
  A. Original patient/source content.
  B. Language-neutral structured fact/concept.
  C. Replaceable display translation.

The display translation never overwrites A or changes B.

Supported active languages:
  en  English  LTR
  hi  Hindi    LTR

Registered coming-soon languages:
  ta Tamil, te Telugu, mr Marathi, bn Bengali, gu Gujarati,
  kn Kannada, ml Malayalam, pa Punjabi, or Odia, ur Urdu.
  Urdu is marked RTL for future work; no complete RTL workflow is claimed.

Central pieces:
  packages/shared/src/language.ts
    Registry, support states, direction, capability flags, and matched en/hi locale keys.

  apps/api/src/language/language-detection.ts
    Bounded English/Hindi/Devanagari/Romanized-code-mix detection with confidence/uncertainty.

  apps/api/src/language/glossary.ts
    Versioned concept IDs, English/Hindi terms, synonyms, transliterations.

  apps/api/src/language/clinical-normalizer.ts
    Maps approved phrases to language-neutral concepts, duration, severity, negation, and clarification.

  apps/api/src/language/translation.ts
    Provider and batch interface backed by approved resources. Unknown clinical prose falls back to the original.

  apps/api/src/interview/question-localization.ts
    Localized question text/options while preserving language-neutral optionValues.

Examples:
  "abdominal pain" and the Hindi equivalent map to SYMPTOM_ABDOMINAL_PAIN.
  "Pet mein three days se pain hai" maps to abdominal pain + 3 days.
  Hindi "I do not have fever" preserves fever=NO.
  "Pet kharab hai" is deliberately ambiguous and requests clarification.

Stored language metadata:
  - Patient/doctor preferred language.
  - Interview original/detected/display language and display text.
  - Voice detected languages.
  - Document and document-fact original/detected language.
  - Optional fact displayTranslation.

Limitations:
  - English/Hindi support is bounded to implemented resources/workflows.
  - No measured clinical-translation accuracy is claimed.
  - Transliteration/code-switching is phrase based, not universal.
  - TTS has an abstraction but is not advertised as available.

22. PROVENANCE RULES
--------------------

1. Never replace original patient wording with normalized text.
2. Never replace original OCR/source evidence with display translation.
3. Source describes origin; verification describes later human review.
4. AI_STRUCTURED and DOCUMENT_EXTRACTED are not doctor verified.
5. A corrected normalized value retains the original value in evidence/history.
6. Unknown is not negative.
7. Missing is not resolved.
8. Historical is not automatically discontinued.
9. Temporal association is not causation.
10. Confidence describes extraction/interpretation quality, not medical certainty.
11. Timeline, comparison, brief, and queue records are derived views, not replacement source records.
12. Downstream derived views are marked stale or rebuilt after source changes.


23. SECURITY AND PRIVACY MODEL
------------------------------

Implemented safeguards:
  - HMAC-based opaque patient session proofs.
  - Signed doctor proof plus active role lookup.
  - Server-side patient/session/visit ownership resolution.
  - Zod validation of bodies, parameters, queries, and controlled enums.
  - Helmet headers and configured CORS origin.
  - 1 MB JSON/form body limits.
  - Audio/document byte, MIME, extension, signature, timeout, and path controls.
  - Private document storage; storage keys omitted from DTOs.
  - Raw voice audio is not retained by HELIOS.
  - Request IDs on logs and errors.
  - Authorization/cookies/bodies/patient-shaped fields redacted from logs.
  - Operational language/provider logs exclude patient text.
  - Append/immutable verification and audit records.
  - Optimistic concurrency and idempotency for doctor actions.

Not production-complete:
  - Production clinician login/identity federation.
  - Care-team/purpose-of-use authorization.
  - Formal threat model and penetration test.
  - Encryption/key-management deployment proof.
  - Retention, deletion, backup, incident response, vendor, and legal policy implementation.
  - Regulatory or medical-device validation.

31. LOGGING, ERRORS, AND AUDIT
------------------------------

Request logging keeps:
  request ID, method, path, status, duration, timestamp, level.

Provider operation logs may keep:
  operation, provider/model identifiers where allowed, status, latency, normalized error code.

Do not log:
  authorization, cookies, request bodies, audio bytes, document bytes,
  transcript text, OCR text, extracted patient entities, source evidence,
  unsafe client filenames, secrets, or unnecessary patient identifiers.

Error policy:
  - AppError carries status and stable code.
  - Zod errors become structured validation failures.
  - Production responses omit stacks.
  - Every error response includes requestId for correlation.

Audit policy:
  - Clinical mutations and important views/rebuilds create purpose-built metadata records.
  - DoctorVerification holds immutable clinical decision evidence.
  - AuditLog should stay metadata-minimized and must not become a duplicate clinical record.


32. HOW TO ADD A FEATURE WITHOUT BREAKING THE ARCHITECTURE
----------------------------------------------------------

Adding an API operation:
  1. Define/update a shared DTO only if both API and web need it.
  2. Add a Zod schema in apps/api/src/validation.
  3. Add repository methods for database work.
  4. Add service behavior for authorization/workflow/transactions.
  5. Add controller translation and standard envelope.
  6. Add route with validation/auth/upload middleware in correct order.
  7. Add API/service/repository/security tests.
  8. Update endpoint docs and ground-zero guide if public architecture changes.

Adding a clinical source field:
  1. Decide authoritative source model and provenance.
  2. Preserve original and normalized values separately.
  3. Use an additive Prisma migration.
  4. Update serializers; do not return raw Prisma objects.
  5. Update TimelineEventBuilder.
  6. Decide whether comparisons snapshot/match/compare it.
  7. Decide whether Clinical Brief selects it.
  8. Add it to verification only with an explicit correction allowlist.
  9. Add unknown/conflict/evidence/security tests.

Adding a language:
  1. Keep it COMING_SOON until completed.
  2. Add registry profile and correct text direction.
  3. Add every locale key with matching placeholders.
  4. Add every relevant interview question/option translation.
  5. Add governed glossary/transliteration fixtures.
  6. Add detection and mixed-language tests.
  7. Validate speech provider support and error behavior.
  8. Add document examples.
  9. Run accessibility/responsive checks, including RTL when relevant.
 10. Run locales:validate and all tests before changing status to SUPPORTED.

Adding an AI/provider adapter:
  1. Implement the narrow provider interface behind a service.
  2. Keep keys server-only.
  3. Enforce timeouts and bounded inputs.
  4. Require strict structured output when returning facts.
  5. Validate output, retry at most within documented bounds, then fall back.
  6. Store provider metadata/provenance without logging patient content.
  7. Ensure model output cannot verify, diagnose, recommend, or control workflow.
  8. Evaluate independently before making quality claims.


33. TROUBLESHOOTING MAP
-----------------------

Health says not_configured:
  DATABASE_URL is absent/unusable. Health can still run, but domain APIs cannot.

Prisma client/type mismatch:
  Run pnpm db:generate, then pnpm typecheck.

Migration failure:
  Confirm PostgreSQL is running, DATABASE_URL database/schema exists, and earlier migrations are applied in order.

Browser cannot call API:
  Check NEXT_PUBLIC_API_URL, API PORT, WEB_ORIGIN, and CORS origin match.

Patient gets forbidden on voice/document/timeline:
  Check x-session-token, session ID ownership, patient binding, and whether localStorage belongs to another/reset session.

Doctor gets unauthorized/inactive:
  Check demo sign-in token, DOCTOR_DEMO_ACCESS_CODE, User role/status, and x-doctor-token.

Voice unavailable:
  Check browser MediaRecorder support/permission, secure context, supported MIME, size/duration settings, SPEECH_PROVIDER, key, and timeout. Text fallback should remain usable.

Document rejected:
  Check max size, extension, MIME, file signature, rate limit, ownership, duplicate hash, storage path permissions, and OCR timeout/provider.

Document processing failed:
  Original remains stored. Retry processing without re-upload or upload a clearer copy.

Interview repeats/clarifies:
  Inspect persisted facts for NOT_ASKED, UNKNOWN, or CONFLICT and question dependency conditions. This may be intended conservative behavior.

Comparison/brief says stale:
  A source or verification revision occurred. Regenerate comparison/refresh brief after timeline/source dependencies update.

Locale validator fails:
  Match English/Hindi keys exactly, remove duplicates/extras, preserve placeholders, and keep codes in the registry.

Tests skip database integration:
  Configure the integration URL expected by tests and provide a disposable PostgreSQL database.
